# Construction and dependency reconstruction

The construction produced `snaky19.compact.cards.txt`: 3,468 ordinary cards,
root 3,467, height 19, empty initial Maker requirements, and first move `(8,8)`.
Its root support has 249 cells in the square `[0,16]²`. Its SHA-256 is
`baf8774e1fc6eea60b1756437e8b3caae0ede5e001b10c0c3787aab51840782e`.
The single delivered copy is `../certificate/snaky19.cards.txt`. Intermediate
`*.cards.txt` files in this construction directory are generated by the commands
below and ignored by Git; they are not additional required proof artifacts.

The independent implementation in `../verification/verify_cards.py` accepted
this exact file. Its result is `../verification/snaky19-compact-audit.json`:
3,468 reachable cards, 61,040 inside replies, 3,456 outside replies, and root
height and dependency depth both 19. That computational check and the
semantic argument in `../SOUNDNESS.md` are separate from the constructor.
This directory does not assert optimality or a proof-assistant kernel result.

## What changed mathematically

The original twenty-move policy repeatedly forgets earlier Maker stones and
safe cells when it switches to a smaller tactical template. The constructor
retains the full Maker set `M`, the actual Breaker set `W` within a fixed
initial support `U`, and therefore the safe set `E = U \ W`.

At a node with a remaining budget `b`, it searches the two existing catalogs
for a transformed card with height at most `b`, required stones contained in
`M`, and support contained in `E`. If such a card exists, that existing proof
is used immediately. Otherwise it makes the baseline policy's move and
recurses only where the baseline hint is too tall for the remaining budget.
All other replies retain their existing certified hints. Outside `U` is one
safe response class; cells inside `U` are tracked separately even when they
lie outside the current baseline template.

The successful run has 180 catalog substitutions. All 180 use at least one
safe cell outside the current baseline template; 68 also use an earlier
Maker stone absent from that template's requirements. There are 17 distinct
tactics from the 15×15 catalog, used 164 times, and three from the twenty-move
catalog, used 16 times. The successful run does not use the optional
zero-cost repeated-pivot rule. Its output needs no new certificate rule.

Three early substitutions explain the elimination of the surviving long
branches. These are exact root-frame states and zero-based source IDs:

| Baseline card | Actual Maker stones | Actual Breaker stones | Replacement from 15×15 catalog |
| --- | --- | --- | --- |
| 1702, height 18 | `(8,8),(8,9)` | `(7,8),(9,9)` | Card 28, height 17; next move `(8,10)`; orientation 3, translation `(2,3)` |
| 1036, height 17 | `(8,8),(8,9),(11,8)` | `(7,8),(8,10),(12,8)` | Card 79, height 15; next move `(11,9)`; orientation 1, translation `(14,3)` |
| 1036, height 17 | `(8,8),(8,9),(11,8)` | `(7,8),(8,10),(13,8)` | Card 145, height 14; next move `(9,8)`; orientation 6, translation `(4,12)` |

`shortcut_audit.json` gives the complete tactic inventory, compact/source ID
mapping, extra cells, and representative state witnesses. The run report
retains every substitution with its full state and transform.

Each newly constructed node is exported as an ordinary `(A,S,p,h)` card.
Initially `A=M` and `S=E`; after successful construction the support is
reduced to the required stones, pivot, and union of the used child supports.
All response hints are preserved wherever a reply is still in that support.
The output therefore compiles the history-dependent construction into the
original declarative interface. Independent checking does not rerun the
search or trust the bit-packed matcher.

## Baseline bottlenecks

`analyze_routes.py` reconstructs the twenty-move certificate from the compact
file, recomputes its dependency depths, and enumerates maximum-depth routes.
It does not search for moves and is not a certificate verifier.

The 1,738-card baseline has 15,696 labelled maximum-depth routes through only
59 critical cards. Cards 1737 and 1736 are the only cards on every maximum
route. Root 1737 plays `(8,8)`. Its four height-critical replies are
`(7,8),(8,7),(8,9),(9,8)`; all map to card 1736. In card 1736's own frame, its
two critical replies are `(6,8) -> 1668` and `(7,7) -> 1702`.

Replaying all those routes with full accumulated ownership partitions them:

| First obstruction or outcome | Labelled routes |
| --- | ---: |
| Repeated planned Maker stone | 9,792 |
| Breaker reply already occupied | 2,592 |
| Earlier global Snaky | 864 |
| Legal route needing twenty baseline Maker moves | 2,448 |

The height-16 families are especially informative. Family 1604 accounts for
all 9,792 repeated-pivot routes, first repeating at card 36. Family 1016 has
720 genuine twenty-move routes. Family 1667 has 1,728 genuine twenty-move
routes, 2,592 illegal routes, and 864 earlier wins. Thus merely skipping a
previously owned planned pivot does not prove nineteen moves.

`baseline_routes.json` contains the critical subgraph, exact reply labels,
transform compositions, per-node path counts, and representative legal
twenty-move transcripts. An outside-support reply in those transcripts is
represented by an explicit distant point, suitable for the infinite board.

## Reproduction

Run from the repository root with Python 3.9 or later and only the standard
library. Sources are the vendored files in `../reference/`; their provenance
and hashes are documented there. The inspected gotrevor reference commit was
`b18ed32473a6a22ebfdda98da62d61b8b1590c1e`.

```sh
python3 topics/snaky/constructor/analyze_routes.py topics/snaky/reference/sieben-20-cards.txt --output topics/snaky/constructor/baseline_routes.json
python3 topics/snaky/constructor/history_closure.py topics/snaky/reference/sieben-20-cards.txt --extra-catalog topics/snaky/reference/gotrevor-15x15-cards.txt --budget 19 --seconds 120 --nodes 2000000 --output topics/snaky/constructor/history_closure_combined_catalog.json
python3 topics/snaky/constructor/prune_certificate.py topics/snaky/constructor/history_closure_combined_catalog.cards.txt --output topics/snaky/constructor/snaky19.compact.cards.txt --map topics/snaky/constructor/snaky19.compact_map.json
python3 topics/snaky/constructor/audit_shortcuts.py topics/snaky/constructor/history_closure_combined_catalog.cards.txt topics/snaky/constructor/history_closure_combined_catalog.json topics/snaky/constructor/snaky19.compact_map.json --output topics/snaky/constructor/shortcut_audit.json
python3 topics/snaky/verification/verify_cards.py topics/snaky/constructor/snaky19.compact.cards.txt --max-root-height 19 --json
```

All searches use one thread, deterministic ordering, no random seed, a
120-second wall limit, and a two-million-call cap. The recorded successful
run used Python 3.9.6 and took 14.90 seconds: 36,084 calls, 180 catalog leaves,
35,751 automatic baseline leaves, and 153 constructed internal cards.

The unpruned file has 10,562 cards: both source catalogs plus 153 new cards.
The compact file retains 1,662 twenty-move-source cards, 1,653
15×15-source cards, and all 153 new cards. Pruning changes only reachability
and indices. `snaky19.compact_map.json` records every old and new ID, source
ID, and both file hashes. It puts children before parents.

## Failed mechanism and checks

The original-catalog-only run first reached a 100,000-call limit after 4.78
seconds; almost all calls were cheap baseline leaves. With the cap raised to
two million, it stopped at an uncovered state after 6.81 seconds. It had
found 286 shortcut leaves and constructed 645 internal nodes, but did not
close the root. `history_closure_20_catalog.json` preserves its exact failure
state and root transcript: baseline card 83, eighteen Maker stones, eighteen
Breaker stones, and one Maker move remaining. This is a limitation of that
mechanism, not an infinite-board lower bound. The later combined-catalog run
closes an earlier prefix using the additional tactics.

The constructor's four focused tests passed once:

```sh
python3 -m unittest discover -s topics/snaky/constructor -p 'test_*.py'
```

They cover all eight orientations, blocked support, forbidden row wrapping
in bit coordinates, imported-card ID offsets, and pruning a catalog with
forward references. Acceptance and deliberate negative controls belong to
the independent verifier. A final result is the compact certificate, its
semantic soundness argument, and that independent acceptance record; a
constructor success message alone is insufficient.
